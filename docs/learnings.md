## Phase 1: Vertical Slice — Sky Data Pipeline — 2026-08-02
- The HYG star database (`hygdata_v41.csv`) includes the Sun itself as row `id=0` with `proper="Sol"`. Must be explicitly filtered out in `scripts/build-star-catalog.js`, or it shows up as a "famous star" in the output (caught live: it appeared at ~38° altitude during daytime testing).
- TypeScript 7 (installed as `^7.0.2`) removed `moduleResolution: "node"`/`"node10"` entirely. `moduleResolution: "node16"` requires `module: "node16"` too, and then even a CommonJS project must use explicit `.js` extensions on relative dynamic `import()` calls. The combo that avoids all of this for a plain CommonJS/tsx project is `module: "commonjs"` + `moduleResolution: "bundler"`.
- `astronomy-engine`'s `Horizon(date, observer, ra, dec)` nominally wants "of-date" equatorial coordinates, but feeding it J2000 catalog RA/Dec directly for fixed background stars (no precession correction) is an accepted simplification here — precession drift is only ~0.4° over 26 years (J2000 → 2026), negligible except for objects sitting almost exactly on the horizon.
- Chrome MCP cannot reach `localhost` on this machine (confirmed again this session) — verified the frontend headlessly instead: load `public/index.html` in jsdom, `dom.window.eval()` the real `app.js`, and point `window.fetch` at the real running Node server. Node's built-in `fetch` requires an **absolute** URL — `window.fetch("/api/...")` throws unless wrapped as `(url, opts) => fetch(new URL(url, "http://localhost:3000/"), opts)`, since Node has no browser `window.location` to resolve relative URLs against.

## Inspection — 2026-08-02 (Phase 1)
- **`__dirname`-relative asset paths break under compile.** `stars.ts` loads the catalog via `path.join(__dirname, "..", "..", "data", "stars.json")` and `server.ts` serves static via `path.join(__dirname, "..", "public")`. In dev (`tsx watch src/server.ts`) `__dirname` is under `src/`, so both resolve. Compiled (`node dist/src/server.js`) `__dirname` is under `dist/src/`, so they resolve to `dist/data/` and `dist/public/` — which `tsc` never creates. Result: `npm start` (the documented prod command) 500s every request and 404s the page, while all 17 tests + `npm run dev` stay green because vitest/tsx run against `src/`. Classic tests-pass-production-breaks. Fix: point paths at the repo root (`process.cwd()` or an env-configured root) rather than `__dirname`, or copy `data/`+`public/` into `dist/` during build.
- Live-running the *compiled* artifact (`npm run build && npm start`), not just `npm run dev` and the test suite, is what surfaced the dist-path bug. Verifying only the dev path would have missed it entirely.

## Phase 1 fix-now follow-up — 2026-08-02
- Fixed both `__dirname`-relative paths (`src/sky/stars.ts`, `src/server.ts`) to resolve from `process.cwd()` instead — both `tsx` and `node dist/src/server.js` are always launched from the repo root via the npm scripts, so this holds in both dev and compiled/prod modes. Re-verified live: fresh `rm -rf dist && npm run build && npm start` now returns real 200s with real star/planet/galaxy data and serves the static page, not 500s.
- Side effect of the first real `npm run build`: `tsc` also compiles `test/**` into `dist/test/**` (tsconfig's `include` covers both `src` and `test`), and Vitest's default file discovery then picks up those compiled `.js` test files too, which crash immediately (`vitest` can't be `require()`'d from CJS output). Fix: added `vitest.config.mts` excluding `dist/**` from test discovery. Used a `.mts` extension (not `.ts`) so Vitest loads the config as ESM without a CJS/ESM warning, since the project's `package.json` has `"type": "commonjs"`.
- Two items from this review were scoped to Phase 5 rather than fixed now, since they're deployment-hardening concerns and Phase 1 never claimed to be deployment-ready: `express-rate-limit` needs `app.set('trust proxy', ...)` to key on the real client IP once behind a load balancer/CDN (currently keys on the proxy's IP, one shared bucket), and there are no `helmet` security headers yet. Both noted in `docs/plan.md` Phase 5.

## Phase 2 planning (pre-verified before build) — 2026-08-02
- `astronomy-engine` bundles the official IAU-88 constellation boundary data internally (`Constellation(ra, dec)`, `ConstelBounds`/`ConstelNames` in its source) — Phase 2 doesn't need to source a separate boundary dataset at all, meaningfully de-risking the phase originally flagged as the timeline's biggest risk. Verified live: a 2° alt/az grid-sample (8,280 points) finds the same constellation set as a 0.5° grid (130,320 points) in ~15ms.
- `Astronomy.VectorFromHorizon(sphere, date, "normal")` **hangs indefinitely at exactly altitude=90°** (confirmed by bisecting a 2-minute timeout down to the single failing point). Fix: pass `null` for refraction instead — also the more correct choice for direction-only classification, since refraction doesn't matter when you only want the true geometric direction.
- `astronomy-engine`'s own `ConstelNames` table misspells 3 of the 88 IAU names: `Ant`→"Antila" (should be Antlia), `Cam`→"Camelopardis" (should be Camelopardalis), `PsA`→"Pisces Austrinus" (should be Piscis Austrinus). Don't display `ConstellationInfo.name` raw — correct these 3 by symbol before showing them to users.

## Phase 2: Constellation Visibility — 2026-08-03
- The pre-verified plan from the prior session's planning was accurate end-to-end — no spec reconciliation needed, no surprises in the algorithm itself.
- `VectorFromHorizon`'s `.d.ts` types `refraction` as `string`, but the implementation (`astronomy.js`, `else if (!refraction)`) treats `null`/`undefined`/falsy as "no refraction" — a real gap between the shipped types and shipped behavior, not just stale docs. Under `strict: true` this requires a `null as unknown as string` cast at the call site; a plain `as any` would also work but is broader than necessary. Documented inline with a comment since the WHY (upstream typing bug, confirmed by reading `astronomy.js` source) isn't obvious from the call site alone.
- `data/stars.json` already carries HYG's own `con` (constellation) field per star, populated straight from the raw CSV — but the plan deliberately classifies stars via `Astronomy.Constellation(raHours, decDeg)` instead of trusting that field, so star tags and the grid-sampled visible-constellation list share one boundary source of truth (avoids an edge-case where a star's HYG-assigned constellation and astronomy-engine's IAU-88 boundary calc disagree at a boundary line, which would show a "famous star in Foo" not present in the "visible constellations: [...]" list). The HYG `con` field is left in the catalog JSON/type unused — harmless, not worth stripping for this phase.
- Live-verified against real references: for London (51.4769, -0.0005) at 2026-01-15T20:00:00Z, the computed 46-constellation set lines up with well-known January-evening-sky facts (Orion/Taurus/Cassiopeia dominant, summer constellations like Scorpius/Sagittarius correctly absent) [sourced: WebSearch — constellation-guide.com, earthsky.org]. Sydney (southern hemisphere, summer evening) correctly surfaces southern-only constellations (e.g. "Apus") and shows the corrected "Antlia" spelling live. A summer-solstice noon London request (sun near zenith) completes in ~80ms with no hang, re-confirming the Gotcha 1 fix holds under the exact condition that used to trigger it.

## Inspection — 2026-08-03 (Phase 2)
- **The 2° grid's "proven sufficient" claim held for one observer, not the input space.** The plan verified 2° == 0.5° for a single London fixture and recorded "2° is proven sufficient, not a guess." A live sweep of 162 observer/time cases (lat −80..80 × lon −180..120 × 3 dates) found 2° misses a constellation that 0.5° finds in **32/162 (~20%)** cases — always near-horizon slivers, always *under*-reporting (never a false positive) [sourced: /inspect grid sweep this session]. This is the core spec-fidelity gap for Phase 2: spec §Sky-Calculation demands "precise IAU-88 boundary polygons intersected with the local horizon," and near the horizon the coarse grid steps over constellations that are genuinely above alt=0. Generalizable: a sampling/resolution parameter validated on one input is not validated for the input space — sweep before writing "proven sufficient."
- **Cheap fix quantified live:** uniform 1° still misses in 12/162 (~7%, 18.5ms); uniform 0.5° is 79.8ms; a **hybrid** (2° over the full hemisphere + a dense 0.5° band over alt 0–5° where all the misses live) matches 0.5° in **0/162** at **9.7ms** — ~2× the current 4.9ms, vs 16× for uniform 0.5° [sourced: /inspect grid-cost timing this session]. The misses are all near-horizon, so densifying only the horizon band recovers them at almost no cost.
- **The exact-set fixture is coupled to grid resolution.** `test/constellations.test.ts` pins `EXPECTED_VISIBLE_CONSTELLATIONS` to the exact 46-name output of the 2° grid. Changing the resolution to close the gap above will change that set for affected observers — the fixture must be regenerated as part of any resolution fix, and a stale fixture would make the *more correct* answer look like the regression (see `tests-enforce-spec-not-code`).
- Verified clean: star-tag vs visible-list consistency (0 mismatches across 360 snapshots) and pole inputs lat=±90 (no hang/crash, 17–23ms) [sourced: /inspect sweeps this session].

## Phase 4: Visual Mini Chart — 2026-08-03
- This project's frontend has no bundler/build step (`public/*.js` are loaded via plain `<script src>` tags, no `import`/`export`). To get the spec's required "pure-function unit test... no browser required" for the new dot-positioning logic, `public/chart.js` uses a UMD-style guard — `if (typeof module !== "undefined") module.exports = {...}` — so the same file works unmodified as a global-scope browser script and as a `require()`-able CommonJS module from a vitest test. No jsdom/build config changes needed.
- Chrome MCP still cannot reach `localhost` on this machine (consistent with the Phase 1 finding). Verified the rendered chart the same way Phase 1 did: load `public/index.html` in `jsdom` with `runScripts: "outside-only"`, `dom.window.eval()` the real `chart.js` + `app.js`, point `window.fetch` at the real running dev server, then inspect the resulting SVG DOM (circle/label counts, computed cx/cy against the raw API's altitude/azimuth). This caught nothing wrong this time, but re-confirms the technique still works on TS7/vitest4/jsdom30 versions.
- Phase 3 (real location input) was not started at the time Phase 4 was built; Phase 4 didn't need to touch it — the chart plugs into the existing `renderSnapshot(data)` re-render path, which is already the single entry point every input path (default-load, and Phase 3's later geolocation/manual-entry) calls after a successful fetch. (Phase 3 has since shipped separately — see below — with no rework needed to the chart.)

## Phase 3: Real Location Input — 2026-08-03
- The plan's own claim that "geolocation grant/deny flows are not meaningfully unit-testable" turned out to be wrong and was corrected during this build (see `docs/plan.md` Phase 3). Confirmed directly: `jsdom` (already a devDependency) has no `navigator.geolocation` at all (`'geolocation' in navigator` → `false`), so the "unavailable" branch is testable with zero faking — more faithful than a manual check, which would require deliberately using an unsupported/insecure context to trigger it for real. The grant/deny branches are testable too, by stubbing `navigator.geolocation` via `Object.defineProperty` (plain assignment fails — TS/jsdom both expose `navigator.geolocation` as a read-only accessor) and asserting the resulting fetch/DOM wiring. Only the real native permission-prompt UI stays manual. Added `test/appGeolocation.test.ts` (jsdom environment) instead of leaving this manual-only.
- Same UMD-style dual-consumption pattern as Phase 4's `chart.js` (see above), applied independently to `public/validate.js` for the client-side lat/long range check — confirms this is now the established pattern for sharing pure logic between the bundler-less frontend and Vitest, not a one-off.
- `jsdom`'s `input.valueAsNumber` correctly returns `NaN` for both an empty and a non-numeric `type="number"` input — confirmed directly before relying on it. This initially let the manual-entry form skip HTML5 `required`/`min`/`max` entirely, so blank and out-of-range values both flowed through the same `Number.isFinite` check and the same inline-error UI path. **Revised in the Phase 3 hardening pass:** added `required`/`min`/`max` back for their accessibility/mobile-numeric-keypad value, but paired with `novalidate` on the `<form>` — confirmed live that without `novalidate`, jsdom (matching real browsers) blocks the `submit` event entirely on a constraint violation, so the custom inline-error handler never runs; `novalidate` disables that auto-block while leaving the attributes in place as semantic/native-validity metadata (`input.validity.rangeOverflow` etc. still populate correctly), so the one inline-error UX path is preserved.
- `@types/jsdom` had to be added as a devDependency — `jsdom` itself ships no types (`package.json` has no `"types"` field), so importing `{ JSDOM }` from a `.ts` test file fails `tsc` under `strict: true` without it, even though runtime behavior (already used ad hoc via plain `.js`/inline scripts in prior sessions) was unaffected.
- Test/appGeolocation.test.ts needs a `// @vitest-environment jsdom` docblock per-file, since `vitest.config.mts` doesn't set a global test environment (defaults to `"node"`) — this project intentionally keeps most tests in the fast default `node` environment and opts individual DOM-dependent files into `jsdom`.

## Phase 4 fix-now follow-up — 2026-08-03
- Live review caught a real bug the unit test missed: the initial Phase 4 build labeled *every* dot, which is fine for a small demo snapshot but produces ~220 overlapping labels for a real sky (all catalog stars visible at once). `test/chart.test.ts`'s pure-function test only ever checked 1-5 items, so it couldn't have caught this — a bug in "how many things get rendered," not in the positioning math, needed a render-level smoke test (`test/chartRender.test.ts`, a ~200-object jsdom fixture) to surface.
- Fix: cap labels to the 10 lowest-magnitude (brightest) stars; planets/galaxies have no magnitude data and are always labeled regardless of the cap (few enough — ≤5 planets, 2 galaxies — that they never need capping). Required threading a new `magnitude` field from `CatalogStar.mag` through `FamousStar` (`src/sky/types.ts`, `src/sky/stars.ts`) and into `chart.js`'s per-item output (`null` for planets/galaxies, not `undefined`, so the selection logic has one explicit sentinel to check). Every dot — labeled or not — still gets an SVG `<title>` child so the name is always available on hover.
- Confirmed live against the real London-sky data: 218 dots, 16 labels (the 10 brightest named stars + 4 currently-visible planets + 2 galaxies), all 218 titles present. User confirmed the "10 brightest stars" cap as the shipped policy (spec had explicitly left labeling density as an open design choice).
- Also fixed: azimuth-0/360 ("N") labels were edge-clipped under `text-anchor="middle"` since they sit exactly at the chart's left/right boundary. Added an `anchorForX(x, width)` helper (switches to `start`/`end` within 15 units of an edge) applied to both dot labels and compass ticks — confirmed live that the two "N" ticks now render with `anchor="start"`/`"end"` instead of clipped `"middle"`.

## Phase 3 hardening — 2026-08-03
- **Stale-render race, reproduced live:** `fetchSkySnapshot` had no sequencing guard — since it's called fire-and-forget (not awaited by its callers), two overlapping calls (e.g. the automatic demo-load fetch and a user-triggered geolocation/manual fetch) could resolve out of order, and a slower, older response could overwrite a faster, newer one's rendered result. Fixed with a module-scoped `latestRequestId` counter: each call captures its own id at entry, and bails before touching `statusEl`/`renderSnapshot` if a newer call has since superseded it. Guarded by a new jsdom test using controllable (manually-resolved) fetch promises to force the exact resolve-out-of-order sequence — this needed a custom per-call mock returning a different pending promise per call, not the usual `mockResolvedValue` (which resolves everything immediately and can't reproduce a race).
- Added a `getCurrentPosition` timeout (`{ timeout: 10000, maximumAge: 60000 }`) so a real device/OS location hang falls back to the manual form instead of leaving the "Locating…" button stuck forever — not exercised by any test (would need a real slow/hanging geolocation call), verified by inspecting the options object jsdom's mock received.

## Inspection — 2026-08-03 (Phase 4)
- **Label anti-collision pushes labels off the right edge (reproduced).** `layoutLabelPositions` (in `public/app.js`) only ever nudges labels *rightward* (`x = max(item.x, prevX + MIN_LABEL_GAP)`) with no clamp to `width`. When labeled objects cluster in one azimuth region (a real sky can put the 10 brightest stars + planets toward one horizon), later labels march past `width` and are clipped by the SVG viewBox. Repro: 16 labeled items at x≈330–355 → max label x = 480 vs width 360, **12 of 16 labels clipped off-chart** [sourced: /tmp/repro-labels.js this session]. The `test/chartRender.test.ts` smoke test only asserts label *count* (≤17), never label *x-bounds*, so it can't catch this. Generalizable: a one-directional spreading algorithm needs a bound check, and a count-only assertion doesn't test positioning.
- **Chart replaced the plain object list → stars/planets/galaxies are now visual-only.** Phase 4 swapped the list rendering of stars/planets/galaxies for the SVG chart; their names now live only in per-dot `<title>` (hover) elements. Screen-reader / keyboard users can enumerate the constellation text list but not the visible stars/planets/galaxies — an accessibility regression vs Phases 1–3's plain list. `role="img"` + summary aria-label describes the chart but not its contents.
- **The label-selection/label-layout pure logic lives in `app.js`, unit-untested.** `selectLabeledItems`, `layoutLabelPositions`, and `anchorForX` are pure functions but sit in `app.js` (not the requireable `chart.js`), so they're only exercised through the jsdom render smoke test. These are exactly the functions that produced the earlier over-labeling bug and the edge-clip bug — they belong in `chart.js` behind the same UMD guard, with direct unit tests.
